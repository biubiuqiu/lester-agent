## Your personal Lester

The **Lester** button in the authenticated workspace (bottom right on wide screens, in navigation on narrow screens) opens a separate, persistent assistant panel. Its dialogue and draft stay with you across task, project and settings pages, even after minimizing. `/app` remains the new-task home. Lester can remember preferences, selected-project decisions and work context, then create an independent task or continue an owned previous conversation. It has **no command, file, browser, Skill or approval tools**. Direct task creation is available at `/app`, `/app/new` and within each project.

- Memories are private to the current user/workspace, with optional project scope. Open **Memory** to search, inspect original user quotes, edit, forget or undo. Inferred memories show a quiet undo receipt; automatic inference can be disabled. Explicit “remember this” still works.
- Current memories override older dialogue. Corrections/forgetting prevent old chat from being silently mined again. Forgetting does not delete original chat or change already accepted task snapshots.
- The current selected model produces bounded, independently validated structured output. Retrieval uses explicit topics, Latin words and CJK bigrams, up to 24 relevant facts / 10,000 content characters. At most 128 active memories per user/workspace; no vectors, background ingestion or unlimited context. Old dialogue stays paginated and visible; model history is bounded.
- Task status comes from PostgreSQL and the existing workspace SSE. New delegated tasks use **standard permissions**. Continuations retain their model/Agent/project and use the existing queue while running. Personal dialogue cannot stop, insert into, approve or change a running task's permissions.
- A missing response is checked against its original receipt. Interrupted turns/delegations are never automatically replayed. The memory system does not imply background/lock-screen push on native clients.

Reopening the assistant refreshes saved dialogue and memories while retaining your unsent draft. Memory search explains empty results, and its editor remains scrollable on short screens. Account menus support arrow keys, Home/End and Escape; settings opened from a task or project return to that same place after switching sections.

Existing deployments must back up, stop API writes/active tasks, apply `backend/migrations/000031_personal_assistant.up.sql` after all earlier migrations, and rebuild **API and Web together**. Fresh Compose mounts 001–035; Helm applies SQL externally. Rollback 031 removes personal dialogue, memories and delegation receipts, preserving task conversations, files and effects. See [the architecture and API guide](personal-assistant.md), or open `/docs/usage#personal-assistant` on your deployment.

## Features

- **Bring your own model.** Configure workspace-level providers and encrypted credentials for OpenAI, Anthropic, Azure OpenAI, OpenAI-compatible services, AWS Bedrock, Google Vertex AI, and Microsoft Foundry.
- **Start from a goal.** The centered composer supports model selection, attachments, and pasted images. New conversation returns to the composer without creating an empty conversation. New conversations use Lester; older conversations retain their original persona.
- **Keep the transition continuous.** First submission smoothly moves the composer to the bottom and bridges conversation loading. Failed creation returns it to the center with the draft preserved. Animations respect reduced motion and never delay or retry task requests.
- **Keep interactions legible.** The task home shows three short examples when empty and folds them into a disclosure when a draft or attachment is present; selecting one only fills the draft. It uses brief entrance, focus and example feedback. Conversation options float above the layout on every screen size. The public homepage offers native, illustrative web/document/code previews that also work without JavaScript. Reduced motion skips these animations.
- **Follow work live.** Replies and actual tool activity stream through one workspace-level SSE connection. Elapsed time, stop controls, and one-time unread notifications show progress across conversations. Runs continue until completion, an explicit error, or cancellation, without a fixed model/tool-loop limit.
- **Use a personal Computer.** Each user gets one logical Computer backed by Docker or Alibaba Cloud ACS Agent Sandbox. Each conversation has its own working directory for commands, files, and terminal sessions. Idle Computers suspend and resume on demand.
- **Inspect and refine files.** Browse a directory tree, open up to eight tabs, inspect code with line numbers, and preview text, Markdown, images, PDFs, or HTML. HTML runs in a restricted iframe with source switching; local page links open verified files from the same conversation. Separate-page preview opens the same isolated viewer in a focused workspace, and direct HTML preview responses also enforce an opaque sandbox origin. Download files or reference them with Modify; references pass paths, not automatically injected contents.
- **Follow files as they are produced.** Successful Agent writes, edits and deliverable registration automatically open verified files in the right-side multi-tab viewer; observed inventory changes during a run also cover shell-generated files. Up to eight stable tabs reuse the same path and retain each file’s preview/source choice across refreshes. HTML defaults to the isolated iframe preview and can switch to source; genuine edits refresh even when size/mtime stay unchanged. Arrow keys and Home/End switch tabs; Delete closes the focused tab. Historical/replayed events, missing files, internal runtime files and dependencies do not force tabs open. On phones the file panel opens and can be dismissed to continue the conversation. Previewing never publishes files.
- **Work from deliverables.** After execution settles, HTML pages and Markdown documents from the verified conversation inventory appear together with preview, download, and file-specific **Continue modifying** actions. The Computer's **成果** tab and the phone's direct **成果** button open the same collection; **… → 查看会话文件** and the panel's **文件** tab retain access to other files. Compact cards keep pending-review status visible and expand file metadata, full summaries, downloads, and the explicit HTML deployment action under **详情与更多操作**. The primary Preview button opens rendered content and collapses the directory; the first live output also collapses the directory, while ordinary browsing retains it and closing the final tab restores it. The workspace starts with the conversation in focus and opens a wider preview on first output; its desktop Workspace button toggles the panel while Results and Files stay inside; phones retain a direct Results entry. A compact result receipt in the conversation links to the detailed panel. Later background writes refresh/add tabs without switching the selected file or reopening a dismissed panel. Terminal, Skills and created-Agent configuration remain available through the panel’s Tools menu. Mobile and expanded panels use native modal dialogs with focus restoration, including nested deployment dialogs. The `register_deliverable` tool records a real HTML/Markdown entry with a title, Agent-authored summary, source run, and entry SHA-256. Re-registering a path preserves its ID; each conversation supports up to 200 records. Registered entries appear first, joined with the verified current inventory; type-based discovery remains for older files and excludes dependency, hidden, Agent-resource, and common support documents such as README/AGENTS/SKILL. Explicit registration can designate a Markdown document as a deliverable. Missing files never become phantom cards. Registration and its digest do not prove validation, preserve historical contents, or publish anything; previews show current files. Other changed files remain in a collapsed related-files list. Partial synchronization and failed/stopped runs are disclosed.
- **Manage models on demand.** Personal settings show the saved model list when an enabled personal or shared model exists. **添加模型** opens the setup form; **服务商连接 → 添加连接** adds another provider. First setup still proceeds through connection and Model ID, and saving does not verify provider access. Administrator shared-model controls remain separate.
- **Keep your place.** Resize the desktop Computer panel, collapse the conversation rail, search conversation titles, and focus previews. Narrow screens have a dedicated file panel. Reading history does not force-scroll to new output; a jump control takes you back when ready.
- **Continue across navigation.** Drafts, file references, tabs, preview modes, expanded directories, and transcript/source reading positions are restored within the current browser tab. File updates do not steal selected tabs or reset source reading positions.
- **Add conversation Skills.** Install packages from the Skill marketplace into a conversation, then let the agent load their instructions when needed.
- **Organize projects.** Every workspace starts with a default project. Create and rename projects, pin projects and conversations, and move conversations between projects without moving their Computer files.
- **Publish HTML artifacts.** Deploy a single HTML file or a static directory, including local images and videos, to durable S3-compatible storage. Share a public URL and manage deployments on the dedicated Artifacts page.
- **Manage your profile.** The account menu groups profile, model, Computer, and Skill settings. Display names, uploaded avatars, built-in themes, linked Google/GitHub identities and passwords can be managed in **个人资料**.

**Recent conversations** in the sidebar lists conversations across projects by latest activity, shows their current project and supports searching conversation titles or project names. Select a conversation to return to its draft and files. The secondary [Task status view](#cloud-tasks-recovery-and-usage) brings together pending reviews, background commands and source-labeled model usage across conversations.

The executor is separated from the conversation service but still runs inside API. Critical run transitions, events, and outbox intents commit atomically in PostgreSQL. Redis publication failures retain events for retries with stable IDs; clients deduplicate repeats. Graceful shutdown interrupts runs and releases their guards without replaying tools. An independent Worker and automatic task resumption are not implemented.

Task-file cards appear after a run finishes, fails, or stops, and only reference files confirmed to exist. The right-hand file inventory and previews keep updating during execution. You can draft the next message during a run, but cannot send overlapping runs in the same conversation.

The composer grows with the draft up to about six lines. During a run, typing keeps text, selected context and attachments in the draft; explicit Enter or Send to queue accepts the next task. Pending attachments show file size, raster-image thumbnails and an enlarged preview. Files over 25 MiB are rejected before submission, and identical repeated selections are skipped. Click a selected context chip to inspect its current content/version; Delete or Backspace removes a focused chip, and Backspace in an empty composer focuses the last chip first.

Assistant replies support plain and formatted copying, and code blocks and source previews have separate copy actions. Success appears only after clipboard writing completes; failures provide a manual-copy fallback. Select text in a response, Markdown preview or source preview and choose **Quote and ask** to append a visible quotation to the existing draft and focus the composer without sending. Source quotes include the path and line range; selections over 6,000 characters explicitly quote only the first 6,000.

Unseen file updates have a tab dot that clears after successful reading and viewing. **Reopen the last closed tab** restores a still-existing verified file and its preview mode/source or Markdown reading position. Up to eight closed tabs are retained per conversation in tab-local view state; reopening never reverts file edits.

## Scheduled tasks and inbound webhooks

Open **Automations** from the account menu or **Manage automations** under **Recent conversations → Task status**. Select the project, model, Agent, task instructions and permissions. Schedule one execution, daily/weekly work or a five-field Cron expression in an IANA time zone. New definitions are disabled unless explicitly enabled. Repeating tasks follow daylight saving time; one-off dates use the browser's local time. The server checks persisted triggers about every ten seconds and creates an independent conversation for each execution. **Run now** explicitly accepts one manual event, including while the schedule is paused.

If an earlier task, pending question/approval or active/unknown background command remains, scheduled occurrences are recorded as skipped; webhook/manual events wait in acceptance order. Missed periods during downtime coalesce into one occurrence. Pausing/deleting cancels pending events; stop already-dispatching tasks in their conversation. Each trigger snapshots task configuration, while ordinary conversation acceptance snapshots current project rules and Agent resources. Account/membership and model access are checked again before execution. Standard permissions can wait for confirmation; auto approval/full access require an explicit selection and retain the existing Computer boundary.

Choose **Webhook** to obtain a generic inbound endpoint and a one-time secret. Store the secret securely on the sender and use HTTPS in production:

```bash
# Set LESTER_WEBHOOK_SECRET securely on the sender; do not put it in the URL.
curl -X POST 'https://lester.example/api/v1/hooks/<automation-id>' \
  -H "Authorization: Bearer $LESTER_WEBHOOK_SECRET" \
  -H 'X-Lester-Event-ID: issue-123-created' \
  -H 'Content-Type: application/json' \
  -d '{"issue":123}'
```

The body must be a JSON object up to 32 KiB. Its contents are task data and cannot change permissions, workspace, model or references. Reusing an event ID with the same canonical JSON returns the original receipt; different data conflicts. Credentials are stored only as hashes, shown only on creation/reset and rotated explicitly. Cookies and query parameters do not authenticate webhooks. Limits are 100 definitions per account, 30 new manual/webhook events per minute per definition and 20 pending events per definition; duplicates do not consume a new-event slot. History shows the last 20 triggers and opens their actual conversation. An uncertain start only checks the original submission receipt; it never starts the same event again. This interface does not include outgoing callbacks or native GitHub/other-app webhook adapters.

Existing databases: back up, stop API writes/active tasks, apply every missing migration through `000029_conversational_schedules.up.sql` in numeric order (including 027–029), then rebuild **API and Web together**. Fresh Compose now mounts every migration 001–035, including the previously missing 016–026 initialization mounts. Do not delete volumes. Rolling back 027 deletes automation definitions/trigger records but preserves conversations, files and already-performed operations. Executor and scheduler remain in API; this does not provide automatic continuation after an API crash. [Behavior, API and recovery details](automations-and-questions.md).

You can also schedule work directly in a conversation: **“Every Monday at 9 a.m., generate a review checklist in the Product project.”** Lester uses `list_schedules` and `propose_schedule` to show a compact card above the composer, with time zone, project, next occurrence and expandable task/model/permission settings. Only an explicit confirmation creates, updates, pauses or resumes the schedule. New schedules use the active task model and Agent with standard permissions; updates retain the existing model, Agent and permission mode. Browser time zone is a saved hint; an explicitly requested zone wins, and missing information is clarified. Each occurrence uses a standalone saved prompt in a new conversation, without inheriting chat history, files, attachments or @ references.

Confirmation and configuration commit in the same database transaction. Stale revisions or expired reviewed occurrences require a fresh proposal; a lost response is reconciled from the original interaction receipt without automatically resending. Schedule confirmation never approves a Plan or expands tool permissions. This is native Agent tooling; no Skill installation is required. Optional Skills can describe reusable task methods, while the server scheduler owns timing and persistence. Apply migration **029** before deploying the new API/Web. Its rollback refuses while schedule interaction history exists; archiving a receipt does not undo an applied schedule or task.

Pending structured questions now stay directly above the composer. They support one to three questions, single/multiple choices, an optional recommendation, free text alongside selections, keyboard navigation and a final review for multiple questions. Recommended choices are never preselected. Answers survive reloads, never approve Plan/tools, and remain inspectable as conversation receipts. Stop and the ordinary chat draft remain available.

## Questions and Plan review

The composer starts tasks normally. For complex multi-file or architectural work, the Agent can call `enter_plan_mode` before mutations and inspect read-only, list directories and clarify requirements. Small clear tasks can execute directly; model judgment determines when planning is needed. The toolbar no longer asks users to choose an execution mode. Existing API clients can still explicitly request Plan. Server-side checks block shell commands, file changes, publication and other mutations, including aliases and custom tools. Explicit user uploads and Skill installation remain separate actions. A proposed plan can be approved, revised or declined; approval binds its exact stored parameters/version to this active run. The approved scope is restored from platform records after compaction. Normal execution does not ask for redundant Plan approval.

Structured questions collect information separately from approval. Answer drafts survive conversation navigation/refresh. Accepted responses are idempotent, and uncertain responses are confirmed through their scoped receipt without automatic resubmission. Cancellation/failure revokes pending requests. Refresh checks cross-replica session ownership; an abandoned executor is marked interrupted, never restarted by an old answer. Explicit in-run adjustments and next-task queuing remain pending in the alignment record.

Databases already on 001–020 apply `000021_run_interactions.up.sql` once after a backup and stopping API writes. A database on 001–019 applies missing 020–024. Never rerun existing migrations. Stop affected active tasks before rolling back 021 and restore a compatible API/Web; original messages and files remain.

Conversation pages keep messages and results primary. **More conversation options** in the upper-right contains recap, context overview and **Show execution process**. The default reading view keeps current streaming output, final replies and actual failures/cancellations/unconfirmed operations visible; routine narration, successful tool records and context-organization notices live in Execution details. The display toggle reveals the chronological process without changing model context, permissions or execution. Reply copying uses one Copy options entry for plain text and formatted HTML, with success/error feedback. One collapsed **Execution details** entry collects answered questions, command logs, file reviews, approval history, processed follow-ups and supporting files. Pending questions, approvals, queue entries and read failures stay visible; unsettled background commands have a direct inspection entry. Opening these controls never starts or approves a task.

## Running-task adjustments and next-task queue

While a task is running, explicit Enter or **Send to queue** queues the next message; typing alone never queues. Once the draft contains text, **Add to current task** sends a text-only adjustment directly, without an extra menu. With attachments or @ references selected, use the queue instead. An empty draft shows only the separate Stop action. Adjustments become real user messages after a complete tool batch; they do not interrupt or replay commands, change Plan mode, or approve execution. Pending adjustments are checked again before completion. An adjustment supersedes a pending question or proposed plan so the Agent can consider the new requirement.

Pending messages stay attached directly above the composer, in acceptance order, with their current status and a Cancel action. They appear immediately from the confirmed submission receipt, remain visible while the transcript scrolls, and recover on reopening the conversation. Expand a long message to read it; the queue scrolls within a bounded area so the input and Stop control stay visible on mobile. Completed/cancelled receipts fold into a compact history.

Queueing is explicit. Accepted tasks retain the actor, selected model, next-task execution mode, attachments and @ snapshots. The next task starts after successful completion, under the same conversation guard. Failure, stopping or an interrupted predecessor pauses future work; resume is explicit and requires an idle conversation. Actor membership is checked again before dispatch. Held text adjustments can be copied back to the draft without sending. Receipt loss preserves the draft and checks the original ID rather than replaying a mutation. “Added to current task” means the input was recorded, not that its requested effect has succeeded.

For databases already on 001–021, back up, stop API writes and apply `000022_run_inputs.up.sql` once. Earlier versions apply all missing migrations in numeric order. Stop active tasks and restore a compatible API/Web before rolling back 022; accepted queue records are removed, while messages and files remain. Queue rollback does not undo any file or external effect.

## Task permissions

Choose permissions in the composer independently of Plan mode. New clients submit through `/conversations/{id}/permissions/messages` and `/conversations/{id}/permissions/inputs`; older APIs cannot silently accept and ignore these profiles. **Default permissions** reads ordinary files automatically and asks before file changes and commands. **Auto approval** handles ordinary conversation-file writes/edits automatically and sends every command to a separate, tool-free review call using the current task's accepted model. No separate approval model setup is needed. Sensitive file paths and other protected operations still require user confirmation. **Full access** skips operation prompts within the existing authorized Computer; it grants no host access, account access, network connectivity or exception to Plan/read-only and file safety checks. User-initiated uploads, terminal commands and file editing remain separate explicit platform actions.

The reviewer receives the actual durable command and parameter digest, task goal and recent denied operations as untrusted data, without the Agent's tools or conversation history. Provider requests include a strict JSON Schema for `decision` (`allow`, `deny`, `ask_user`), a short `reason`, and the exact `request_digest`. The server independently rejects extra/missing/duplicate fields, wrong digests, tool calls, prose and malformed responses. `allow` creates a single-operation receipt consumed before execution; `deny` blocks that operation; `ask_user` displays the existing approval card. Provider rejection (including unsupported structured output), a 25-second timeout, oversized review input or invalid output falls back to user confirmation. There is no silent plain-text retry or automatic tool replay. Review calls are included in task model usage as `permission_review`; the review's 1,024-token output bound does not cap the main Agent's output.

The initial mode remains part of the submission identity. During an active run, the selector now updates that run's **remaining operations** through authenticated `GET/PUT /conversations/{id}/runs/{runID}/permissions`, using a revision to reject stale writes. This cannot undo an operation already started. An approval card for a command also offers **Full access for this task**, atomically allowing the waiting operation and updating the run. Queued tasks retain their own captured modes; expand a queued message to inspect its permissions. Live mode changes revoke obsolete review claims and unused receipts; late reviewer output cannot override the new mode, Stop or an adjustment. Full access never bypasses Plan.

The approval card sits above the composer and shows the actual command or target file. Allow once binds the durable tool call and exact parameter digest; ordinary file operations also offer a same-run write/edit grant. Commands use individual review receipts unless the user explicitly selects full access for the active task. Decisions, their source and review reasons remain visible in approval history. Rejection is not permission to retry through another tool or command. Stop and abandoned-run recovery cancel pending user and AI reviews. Lost responses only read the original status; they never replay tools or approval mutations.

Existing databases through 027: back up, stop active tasks/API writes, apply `backend/migrations/000028_permission_reviews.up.sql` once, then rebuild **API and Web together**. Older databases must apply every missing migration in numeric order, including 025–027. Fresh Compose databases initialize 001–035; Helm migrations are applied externally. Do not delete volumes. Rollback 028 requires compatible API/Web, cancels unfinished AI reviews and removes review-specific fields/usage records; it never undoes tool effects, deletes files or removes ordinary execution/compaction usage.

## Session recap and context overview

Existing conversations offer **Session recap** and the local `/recap` command. The recap quotes the latest goal and reply (at most 400 Unicode characters for the reply), shows the observed task state and links recent file-update events to files verified in the conversation inventory. It does not invoke a model, replace the transcript, attest that tests passed, or authorize/replay tools. After at least two minutes away, new activity can open a recap on return; unsent text, attachments and references prevent automatic expansion. Automatic recaps can be disabled per conversation. Preferences and absence markers use the existing account/workspace/conversation-scoped browser storage, cleared on logout.

**Context overview** separates the latest accepted user-message snapshots (references, attachments and versioned project rules) from unsent materials. Referencing a Skill or file is not proof that the Agent loaded or read it; consult tool activity. This view is not the complete provider request or a token counter. **Compact activity** groups three or more consecutive confirmed tool completions; **Detailed activity** keeps individual rows. Failures and unknown outcomes are not grouped as success. Failed or stopped tasks offer explicit recovery instructions added to the current draft, preserving its text; only sending starts a new task under its selected permissions.

## Composer controls and automatic planning

The composer groups attachments, @ references (contexts, conversations and Skills) and Agent selection under **+**. Typing `@` and pasting images remain available. Model selection sits on the right beside the circular Send button; permissions stay visible and independent. New and queued tasks start normally so the Agent can choose planning for each task. Active tasks keep their accepted model; model switching unlocks after completion. Agent-selected planning requires upgraded **API and Web together**, without a new database migration; apply all existing migrations first.

## Cloud tasks, recovery and usage

Open **Recent conversations → Task status** in the conversation sidebar to see the latest task in each conversation. Filter all, active, needs-attention or finished tasks, inspect queued/held counts and registered-deliverable metadata, and open the original conversation for approvals or recovery. Background commands that outlive an Agent reply are listed separately; unknown command outcomes remain needs-attention, and unfinished commands keep that conversation out of the Finished filter. Counts are workspace-scoped and come from PostgreSQL, not from which tabs are open. The list uses stable cursor pages (20 by default, at most 50), polls while visible on the first page and refreshes on existing workspace task events; after loading more pages, use Refresh to return to the latest page. It opens no additional SSE connection. Merely viewing a task never sends a message, approves an operation or resumes work. Background file arrivals still register tabs but do not raise a workspace panel over a modal or an expanded file review. A failed read displays an error instead of an empty list. “Completed” means the run ended, not that its output was accepted or tested; deliverable counts are registration metadata, not verified current file snapshots.

The API now reconciles abandoned runs on startup and in bounded pages of 30 every 15 seconds. Ownership is proven by the existing PostgreSQL session advisory guard, including across API replicas; a quiet or long-running task is never failed merely because of its age. A released owner becomes interrupted/failed (or cancelled if cancellation was pending), unresolved tool outcomes stay unknown, pending approvals/questions are revoked and future queued inputs are held. No tool is automatically replayed. Closing the browser does not cancel a live executor; restarting API still interrupts its in-process execution. Recovery is an explicit new task after checking current results, not transparent continuation through a crash.

Expand **Time and model usage** for elapsed wall time (including waits), model-request count, provider-reported input/output and separately labeled estimates for requests without reported input. Cached input is counted once across provider conventions; compaction requests are included. Missing output counters stay unknown rather than zero, and reported zero output is preserved. There is no monetary cost estimate or billing claim. The authenticated read endpoints are `GET /api/v1/tasks` and `GET /api/v1/conversations/{id}/runs/{runID}/usage`; neither exposes prompts, provider keys or raw provider usage maps.

Existing installations through migration 025: back up PostgreSQL, stop API writes/active tasks, apply `backend/migrations/000026_cloud_task_indexes.up.sql` once and rebuild **API and Web together**. This migration only adds query indexes and preserves all task/file data; fresh Compose initialization includes it. Rollback drops only these indexes. Do not delete volumes. The three delivered cloud priorities and remaining architecture boundaries are described in [Cloud Agent priorities](cloud-agent-priorities.md).

## Product scope

Lester focuses on conversation-driven work. The current version does not include a Workflow/DAG editor or engine, visual orchestration, a multi-agent orchestration UI, Knowledge Base/RAG products, dedicated browser UI, Computer snapshots, or automatic Docker/ACS workspace migration.
