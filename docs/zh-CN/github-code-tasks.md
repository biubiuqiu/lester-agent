# GitHub 代码任务

[文档目录](README.md) · [应用连接](app-connections.md) · [English](../github-code-tasks.md)

任务可以选择已授权的 GitHub 仓库，把源码快照导入 Computer，编辑文件、运行测试、准备发布预览，再推送工作分支或创建 PR。它与只读资料搜索独立；Gmail、X、飞书和 Slack 继续只搜索和读取。个人助理负责把工作委派给普通任务，不直接持有 GitHub 或 Computer 工具。

## 开启代码权限

按[应用连接](app-connections.md)配置 GitHub OAuth client ID/secret。使用已安装的 **GitHub App**，开启仓库 **Contents 读写、Pull requests 读写及 Metadata 读取**，只安装到需要 Lester 操作的仓库。组织策略可能要求管理员批准。没有请求 `repo` scope 的普通 OAuth App 保留公开资料读取，不能提供此代码链路。

在**设置 → 应用连接 → GitHub → 代码任务**里明确授权代码操作。普通连接默认仍只读。开启代码操作只记录 Lester 侧的同意，仓库实际权限、应用安装范围、组织策略与分支保护仍逐次由 GitHub 校验；连接成功不代表所有仓库都可写，也不能借用其他用户的授权。

## 开始任务

例如：

> 在 `owner/repository` 中修复设置页布局。从 `main` 拉取，执行相关测试，然后准备推送新工作分支并创建 PR。

未指定仓库时，Agent 会列出授权账号可访问的仓库，并让你选择。它把固定 commit 的源码导入**当前会话的新目录**，不会覆盖已有目录。本地 Git 仓库包含源码快照的初始提交，方便查看 status/diff；不包含远程完整历史、凭证助手或带认证信息的 origin 地址。

编辑与测试继续用现有文件、命令工具。标准 Computer 镜像包含 Node.js、Python、Go、Git 和浏览器运行环境。只有真实命令结果才能证明测试通过；缺少依赖、测试失败、网络不可用或执行中断都会如实报告。完成授权不代表测试已通过。

发布分两步：

1. **准备预览：**读取明确选中的新增/修改文件和真实删除，生成服务端加密保存的不可变快照，绑定仓库、分支、提交、可选 PR 与摘要哈希，不改变 GitHub。
2. **确认发布：**在现有审批卡核对仓库、分支和摘要。本次任务的提交者需单次明确确认，完全访问模式也保留这一确认。预览准备后，本地再发生的编辑不会改变已经准备的上传；要包含新改动需重新准备。

默认创建新的 Lester 工作分支。明确指定已有分支时，其远端 head 仍需与预期源码一致；并发改动会被拒绝。GitHub 的 expected-head 提交操作防止旧任务覆盖新提交。不强制推送，不自动合并 PR。只有真实收到服务商回执，才会报告提交或 PR 链接。

## 凭证与文件传输

API 使用服务端保存的 GitHub 授权读取固定 commit/tree/blob，并执行发布。源码通过有边界的 ZIP 交给可信 `lester-toolbox` 导入，发布时再读取明确选中的文件快照。专用原生传输协议直接调用固定的工具箱，不加载用户 Shell 启动脚本，也不通过用户可改的路径查找可执行文件。沙箱不会收到 GitHub access token、refresh token、SSH key 或带认证信息的远程地址；本地 Git 和测试接触不到连接器凭证。

每个工作目录绑定本次任务提交者和原 GitHub 授权代次。断开、切换 GitHub 账号、撤销成员关系或停止任务后，旧操作不能继续生效。工作目录和预览限定在对应用户/会话，会话最初的创建者不能把自己的授权借给后续提交者。

首版最多导入 **5,000 个普通文件 / 25 MiB**，单个源码文件最多 **4 MiB**。拉取时接受分支名称，暂不支持直接指定标签或提交 SHA；拒绝 GitHub 截断的目录树、符号链接和子模块，不静默跳过。Git LFS 指针按普通源码读取，不自动拉取 LFS 对象。一次发布最多 **100 项变更 / 1 MiB 文件内容**。已有可执行文件可以导入、运行；选用的 GitHub API 不提供文件模式控制，因此拒绝发布可执行模式文件或模式变更。超大改动可拆分，暂不支持的仓库特性请使用自己的开发环境处理。

## 安装依赖与联网

拉取和推送发生在服务端，即使 Computer 断网，也可以通过工具接收源码、发布选中改动。安装依赖是独立能力。Docker Computer 默认仍为 `none` 断网；部署管理员可把 `SANDBOX_DOCKER_NETWORK` 设为 `bridge`，或更推荐指定已有的专用 Docker 网络，在网络/宿主侧配置依赖访问策略。任务不能自行选择网络；拒绝 host 或借用其他容器的网络命名空间。

该选项只选择网络，不等于实现域名白名单、防火墙、依赖镜像或代理。相关限制由管理员在 worker/网络侧配置并验证。更改只影响**新建** Computer，不替换已有容器；不要删除数据卷或静默替换 Computer 来应用网络配置。ACS 的出网仍由模板、租户网络策略控制，不使用此 Docker 选项。

## 发布结果不确定时

外部变更前先记录持久意图，固定上传内容、预期 head、目标分支和操作标识。响应丢失后，只检查原来的分支、提交和 PR 回执，不盲目重发写请求。待确认或未知不能标成成功；应先核对原发布实际结果，再决定是否准备新操作。打开页面不会自动推送或创建 PR。

## 升级与验证

先备份数据库、对象存储和 Computer 数据卷，停止 API 写入与活跃任务，按顺序补齐迁移到 `000034_speech_input.up.sql`，然后一起重建 **API、Web、Sandbox Service**。保留原加密密钥。新 Compose 初始化 001–034；Helm 需单独执行 SQL。033 的安全回滚只删除代码授权标记、工作目录绑定和预览记录，不删除工作树、不撤销提交或关闭 PR；未确认的发布或审批必须先处理。

Docker 的 Sandbox Service 启动时会原子更新已有 Computer 的 Toolbox，保留工作区数据和运行镜像。ACS 需更新运行时镜像/模板，再显式安排已有 Computer 升级并保留持久工作区。旧镜像或自定义镜像也需要可用的 Git。

后端协议测试使用假 GitHub 服务和真实 PostgreSQL；传输测试使用真实本地 Git；浏览器夹具覆盖授权、审批、恢复和六语言桌面/手机。它们不等于已经完成真实 GitHub App 注册、组织审批、托管 CI，或验证了你的具体仓库依赖和测试。
