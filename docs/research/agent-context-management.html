01

先给结论：管理的是工作集，不是无限记忆

共同模式：长期保存历史，每次只把一个有预算的工作集交给模型。

分层组装 → 限制工具输出 → 估算 / 观测 token → 压缩旧内容 → 重建上下文 → 失败时有界恢复。区别在于谁拥有压缩权、什么必须保留、以及信息丢失后能否找回。

完整记录

会话日志、数据库、JSONL 或分支树。用于审计、恢复与检索；可以比模型窗口大得多。

模型工作集

本轮真正发送的 system、工具 schema、摘要、近期消息和结果。窗口限制作用在这里。

Prompt cache

复用已处理前缀，节约成本或延迟。缓存 token 仍占上下文；只有实际裁剪或压缩才减少工作集。

这是跨项目的分析模型，不代表五个项目使用完全相同的类名或存储结构。[D6] 工具调用配对与模态归一化 · [O4] checkpoint 与历史重建 · [P3] CompactionEntry · [H5] 确定性工具结果裁剪

上下文分层：哪些应当重建，哪些可以总结

L1 稳定指令系统约束、工具定义、仓库规则。压缩后从权威来源重新组装。
L2 当前任务与状态最新要求、未完成工具组、错误、权限 / 运行状态。不可随摘要推断授权。
L3 近期精确上下文最近用户输入、assistant、工具结果。优先原样保留，避免切断调用关系。
L4 历史工作摘要目标、约束、决策、进度、路径、错误、下一步。允许有损，带明确边界。
L5 原始记录与外部文件不必全量进 prompt；按需检索、分页读取、从归档恢复。

上图是一种建议的职责划分。实际实现有差异：Claude Code 会恢复附件与部分文件；Codex 重建 world state；OpenCode 明确要求摘要不复述会单独重新提供的 AGENTS.md 等规则；Pi 依赖会话投影和保留 ID；Hermes 用 session_search 指针恢复被降级内容。

[C4] 完整压缩与恢复预算 · [D4] 本地摘要与历史重建 · [O3] 摘要与原生双路径 · [P3] CompactionEntry · [H6] 尾部降级与恢复指针
不要把跨会话记忆与窗口压缩混为一谈。项目规则、长期偏好和当前会话摘要具有不同生命周期；“存在 memory 文件”并不能证明有完整的总预算控制。
03

Claude Code：多级减量，保留缓存与恢复能力

证据范围：社区公开镜像 alex000kim/claude-code，自述来自泄露源码；本次阅读快照 6aa7e7f87890。未对原始 npm sourcemap 做逐字节溯源，也未验证生产构建与远端开关，因此以下只描述镜像中的代码路径。没有把镜像称为官方开源，也没有在 Lester 再分发其源码。

规则 / 环境 + 历史→条件 microcompact→autoCompact 检查→session memory 或完整摘要→重建附件 / hooks

分层与压缩

  1. 规则独立组装。getUserContext() 读取发现的 CLAUDE.md 与日期；它们不应只依赖历史摘要存续。禁用开关、bare 模式与显式附加目录会改变发现行为。[C5] CLAUDE.md 组装
  2. 先做微压缩。主循环在 autoCompact 之前调用 microcompact。time-based 分支在间隔超过配置阈值时替换旧工具结果；cached 分支依赖构建特性、模型支持与主线程来源，将删除交给 API cache editing 层，保持本地正文不变。没有满足条件时可直接返回原消息。不能写成“所有用户每轮必删旧结果”。[C2] 微压缩分支 · [C6] 主循环调用顺序
  3. 先尝试已有会话记忆。自动压缩路径可优先用 session memory 充当摘要，再保留近期消息。默认边界配置为 minTokens 10,000、minTextBlockMessages 5、maxTokens 40,000；这些是该路径尾部选择参数，并非整轮请求总上限。[C1] 触发阈值与熔断 · [C3] 会话记忆与尾部
  4. 否则运行完整摘要。压缩结果包含 boundary marker、summary、可保留消息、附件与 hook 结果。恢复文件最多 5 个、每个最多 5,000 token；Skill 恢复另有每项与总预算。文件和 Skill 的恢复会重新占用窗口。[C4] 完整压缩与恢复预算

阈值不是固定百分比

W = 模型窗口（可能被 CLAUDE_CODE_AUTO_COMPACT_WINDOW 下调）
E = W − min(模型最大输出, 20,000)
T_auto = E − 13,000
如配置百分比 override：取该百分比阈值与 T_auto 的较小值

因此 W=200,000、输出预留=20,000 时，默认公式阈值是 167,000，而不是简单的 80% 或 90%。这个例子是算术演示，不是对某个线上模型当前默认参数的断言。[C1] 触发阈值与熔断

失败保护与证据边界

autoCompact 有 compact / session_memory 递归保护；连续失败达到 3 次后停止自动尝试，防止每轮重复发送注定失败的压缩请求。完整摘要路径也处理摘要请求本身过长、流中断与用户取消。压缩后清理上下文缓存与相关状态；“旧信息还在磁盘”不代表模型当前可见。部分机制受内部 feature gate 控制，不能由源码存在推导为公开版全部开启。

04

Codex：客户端管理窗口，压缩策略由能力决定

研究的是 openai/codex 中 Rust CLI / agent runtime。不是模型服务端实现，也不等于所有 ChatGPT 产品内部实现。固定快照 61f34c35af77。

指令 / world state + history→窗口与分域预算→能力 / 特性选策略→结果校验与安装→新窗口继续

两种预算视角同时存在

active_context_tokens 是完整活动上下文；auto_compact_scope_tokens 则按配置计整个上下文，或只计新窗口初始前缀后的增长（BodyAfterPrefix）。后者扣除 prefill baseline，不会让完整模型窗口的硬限制失效。窗口 baseline 可以先估算，再被服务端 usage 观测替代。[D2] 完整窗口与分域预算 · [D5] 异步压缩与版本校验

模型自动阈值 = min(显式阈值, floor(模型窗口 × 0.90))
未提供显式阈值时：按 floor(模型窗口 × 0.90)
full-window 检查：active ≥ resolved_window × effective_context_window_percent / 100
另有 body-after-prefix、fallback buffer 与 post-turn 检查

90% 是模型元数据的基础计算，不能代替整个触发逻辑。effective_context_window_percent 默认值在该快照为 95；具体模型、配置与特性会改变有效行为。[D1] 模型阈值计算 · [D2] 完整窗口与分域预算

三条应分开理解的路径

  • 远程 V2 压缩：provider 声明能力时使用；客户端负责发送窗口、接受 replacement history、安装 checkpoint、重建相关前缀。服务端如何编码或筛选信息不在这个开源仓库中，不能据此宣称是某种确定的 LLM 摘要算法。[D3] 压缩策略分派 · [D8] 远程压缩结果安装
  • 本地编排摘要：不支持远程时，客户端组织摘要请求并重建历史；这仍需要模型推理。“local”不表示离线算法。该路径给保留用户消息分配 20,000 token 预算，从较新的消息向前选取，必要时截断，再放入摘要与当前上下文。不能把这套保留规则套用到全部远程策略。[D4] 本地摘要与历史重建
  • TokenBudget 特性：独立分支直接开始新上下文窗口，沿用 compaction 的 hooks / 事件生命周期；该文件明确跳过模型 / 服务端摘要。它不能被描述为普通摘要的另一名称，也不代表默认开启。[D3] 压缩策略分派 · [D7] TokenBudget 新窗口路径
异步候选、历史一致性与超限恢复

异步压缩只在 AsyncCompaction 开启、TokenBudget 未开启且 provider 支持 V2 时适用。后台针对一个前缀生成候选；采用时检查 history generation，防止旧结果覆盖已替换的历史。保留活动 suffix 后仍可能过预算，安装逻辑可走前台回退。

本地摘要请求遇到 ContextWindowExceeded 会移除最早 item 再试，且历史层会处理成对工具项；这意味着压缩输入本身也可能丢失最早细节。正常历史在发送前归一化工具调用 / 结果，移除孤立输出并处理不支持的图片、音频。

[D5] 异步压缩与版本校验 · [D8] 远程压缩结果安装 · [D4] 本地摘要与历史重建 · [D6] 工具调用配对与模态归一化

OpenCode：checkpoint + recent-context，支持原生压缩

研究对象为 anomalyco/opencode 当前 packages/core，快照 f7d5b6ffc482。网上常见的 packages/opencode/src/session/compaction.ts 与旧版 prune 参数，不应不加版本地搬到本次实现。

完整当前请求→auto / manual / overflow→摘要或 native→checkpoint + keepID→历史按边界重建

预算：同时照顾摘要可行性与 prefix cache

W = limit.input，未提供则取 limit.context
显式 buffer：T = W − buffer
默认：T = W − max(floor(W × 0.15), W ≥ 32,000 ? 16,000 : 0)
limit 未知（≤ 0）：自动 ceiling 为 ∞；依赖 provider 拒绝触发恢复
默认 keep = 15,000

keep 是近期文本选择预算，不是摘要上限，也不等于严格限制整个 checkpoint。窗口未知时，压缩请求内部采用 200,000 的假定窗口来规划；这不是对真实模型能力的确认。[O1] 预留量与缩减阶梯 · [O2] 窗口上限公式 · [O3] 摘要与原生双路径

摘要路径

先按 keep 选择近期消息，保存其起点 metadata.keepID。摘要尽量使用未改写的当前请求前缀来复用缓存；更新旧摘要时合并为一个新的结构化 checkpoint。后续模型看到的开头是一个 user checkpoint，含 <summary> 与按引用重建的 <recent-context>，再追加新的消息。近期上下文以文本呈现，与 Pi 直接保留原消息序列的形式不同。[O3] 摘要与原生双路径 · [O4] checkpoint 与历史重建

Provider 原生路径

模型元数据声明 compaction.type === "native" 时，保存 provider 返回的 native.messages replacement window，而不是强行转换成文本摘要。原生不透明项本地无法可靠计 token，代码会等待该窗口后的 provider usage。切换到不能重放该原生窗口的模型 / provider 时，历史读取会回溯重建原始记录。[O3] 摘要与原生双路径 · [O4] checkpoint 与历史重建

请求过长时如何缩小，以及哪些失败不会被当成成功

SHRINK_STEPS 为 0.7、0.5、0.35；overflow 首次就以被拒请求估计大小的 70% 为目标。后续拒绝进一步缩小摘要输入，按 exchange 丢弃较早部分并插入省略提示。它解决摘要请求无法发送的问题，但不能保证摘要涵盖被省略内容。摘要不符合格式可补一次提醒；length、content-filter、空摘要或无效结束原因都进入失败处理。auto=false 同时跳过非手动的自动与 overflow 压缩。

[O1] 预留量与缩减阶梯 · [O3] 摘要与原生双路径

Hermes：双层压力检查，强调可恢复的有损压缩

研究对象 NousResearch/hermes-agent，固定快照 944c3a434071。上下文引擎由 ContextEngine 接口抽象；默认是内置 ContextCompressor，其他插件必须配置后才生效。不能把可选 LCM 插件的能力归到默认实现。[H7] 可插拔引擎接口 · [H8] 维护者文档与网关分层

网关 session hygiene→agent 内压力检查→确定性 prune / 条件微压缩→head + summary + tail→归档 / 检索恢复

先区分外层安全网与内层压缩器

维护者文档将网关 hygiene 描述为约 85% 触发的入站前安全网，Agent 内压缩器处理工具循环内的增长。内层基础配置为 50%，但当前代码对小于 512K 的窗口将有效比例提升到至少 75%，还扣除 max_tokens 输出预留、应用 64,000 的最低触发量及退化小窗口保护、显式绝对 cap / 辅助模型可行性上限。某些 Codex 路由另有提高阈值规则。所以“默认一律 50% 压缩”是错误概括。[H1] 实际触发比例 · [H2] 输出预留与阈值 floor · [H8] 维护者文档与网关分层

减量从便宜的步骤开始

  1. 工具结果裁剪：确定性 prune 可去重字节完全一致的结果，缩短非尾部大结果与参数，处理旧图像。只有回收量足够并经过 rearm 判断才提交，避免频繁改前缀造成缓存抖动。若归档 / 并发校验失败则保留输入。[H5] 确定性工具结果裁剪
  2. 选择受保护头尾：保留头部与最近输入，按预算选择尾部并对齐 tool_call / tool_result。当前 lean 默认尾部预算约为 clamp(2.5% × window, 10,000, 25,000)，还受窗口占比 cap 限制；必要的最后用户 / assistant 锚点和原子工具组可使实际超出目标。protect_last_n=20 不能被读成无条件保留最后 20 条。[H3] 尾部选择预算 · [H8] 维护者文档与网关分层
  3. 生成摘要并附恢复线索：保留标识符、用户要求、决策、进度、路径和恢复指针。lean 尾部中陈旧的大工具结果还可变成指向 session_search 的一行 stub，原内容留在会话历史。持久记录可找回不代表本轮模型仍见到原文。[H6] 尾部降级与恢复指针 · [H8] 维护者文档与网关分层

计量与异常路径

usage anchor 优先使用 provider 已报的 prompt / completion 计数，再估算新追加消息的 delta；不是每次请求的精确 tokenizer。没有 anchor 时，部分阈值 gate 会先等一次 provider 证据；真正的 context overflow 则允许受限恢复。摘要失败有持久 cooldown、无进展保护与分类处理，某些持续失败可降级为确定性 fallback 摘要，abort_on_summary_failure 会改变行为。不能把 fallback 称为保真摘要，也不能把所有失败概括成“静默丢弃中段”。[H9] usage anchor · [H8] 维护者文档与网关分层 · [H4] 摘要上限

文档漂移的直接例子：同一维护者文档仍有“200K × 50% = 100K”的旧计算例，以及摘要最大 12,000 的说明；代码中的比例修正使前者不再普遍成立，当前 _SUMMARY_TOKENS_CEILING 为 10,000。报告采用源码值，并保留文档作为语义与差异证据。[H1] 实际触发比例 · [H2] 输出预留与阈值 floor · [H4] 摘要上限 · [H8] 维护者文档与网关分层

Pi：用会话树和保留边界重建模型上下文

从用户熟悉的 badlogic/pi-mono 地址读取，快照 b9fb2b854b7a；当前源码包名 / 文档链接已经出现 earendil-works/pi，本报告仍固定已获取的 commit，避免名称迁移造成版本混淆。

持久 session tree→当前分支 projection→选择切点→写 CompactionEntry→摘要 + kept suffix

预算与保留语义清楚分离

自动触发：contextTokens > contextWindow − reserveTokens
默认 reserveTokens = 16,384
默认 keepRecentTokens = 20,000
可按 provider/modelId 分别 override 两项预算

reserve 是提前触发的空间，keep 是选近期消息的目标。它们都不是整个请求的最终 token 数。默认切点不能落在工具结果中；工具结果跟随调用一起保留。若单个用户跨度过大，可在 assistant 边界分割，分别概括历史与该跨度的前缀后合并。[P1] 默认预算 · [P2] 阈值与切点 · [P7] 设置与行为文档

CompactionEntry 保存“如何重建”，不是删除旧记录

关键字段为 summary、firstKeptEntryId、tokensBefore，另有 usage / details。后续模型输入由摘要和保留边界之后的消息重建；原始记录仍在 session 中。连续压缩时要把上次幸存的内容也纳入新的总结范围，不能只从旧 compaction 条目后开始而漏掉保留前缀。当前实现还通过 context_edit 处理被省略 / 替换的尝试，投影后的工作集与原始导出记录可以不同。[P3] CompactionEntry · [P7] 设置与行为文档

摘要输入也需要控制大小

序列化阶段把对话转换成带角色与工具标签的文本；思考块不纳入这份摘要输入，工具结果在序列化时限制到 2,000 字符，并标明截断。这是字符规则，不是 2,000 token。文件读写路径累积到 details，帮助后续恢复，但路径清单不等于保留文件正文。[P5] 摘要输入序列化 · [P1] 默认预算 · [P7] 设置与行为文档

分支切换、超限与扩展

切换 /tree 分支可对离开的分支生成 BranchSummaryEntry，按共同祖先定位需要总结的路径；这是分支知识迁移，不应混同自动窗口压缩。扩展可通过 session_before_compact 取消或提供摘要。overflow / 特定 length 恢复在完整生命周期后修复投影、压缩，再以新 run 重试；代码限制一次 compact-and-retry 恢复，失败或取消不应调度内部无限重试。

预算演示：相同窗口，不同触发策略

拖动参数查看公式差异。这里演示触发线，不模拟真实 tokenizer、不调用模型，也不保证压缩后大小。没有把五种策略简单排成好坏；越早压缩通常越省空间，也可能更早丢失细节。

公共 U 仅用于横向算术比较。Claude 用 min(R,20K)；Codex 演示 Total / 无 buffer；OpenCode 无显式 buffer、input limit 等于 W；Hermes 演示默认非 Codex 路由、R 已设置、无外部 cap；Pi 默认 reserve。真实系统的 usage 定义、前缀作用域和特性开关可能不同。

[C1] 触发阈值与熔断 · [D1] 模型阈值计算 · [D2] 完整窗口与分域预算 · [O2] 窗口上限公式 · [H1] 实际触发比例 · [H2] 输出预留与阈值 floor · [P2] 阈值与切点

真正约束的是整个请求

input = system + instruction files + tool schemas
      + summary + recent messages + new user input
      + tool arguments/results + images/audio + protocol overhead

在共享输入输出窗口的协议下：input + output reserve + safety margin ≤ window

自动阈值只能提前减轻压力，无法数学保证每次都不超：新工具结果可能突然膨胀、估算可能偏低、provider 可能更新窗口、原生项不可本地测量、不可压缩的保护集合本身也可能太大。可靠实现需要完整请求重估、provider 拒绝后的有界恢复，以及无法再缩小时显式停止。

建议的验收指标

  • 窗口安全：请求超限率、压缩后仍超限率、连续无回收次数。
  • 任务连续性：用户约束 / 待办 / 精确标识符召回；压缩后误重复工具率。
  • 成本与延迟：压缩推理 token、p50/p95 等待、cache read 比例、同一内容重复压缩率。
  • 恢复能力：模型切换、进程重启、取消、摘要 provider 失败、巨大受保护输入时的行为。

以上指标是本报告提出的评估方案；本次未运行真实模型压缩质量 benchmark，没有跨框架胜负或性能数字结论。

阅读源码时最容易误判的六件事

01

缓存 ≠ 省窗口

复用计算不等于移除输入。区分 prompt caching 与 cache editing。

02

尾部目标 ≠ 最终总量

还要加摘要、schema、稳定指令和新输入；原子工具组也会超出选择目标。

03

本地压缩 ≠ 离线压缩

常指客户端编排 LLM 摘要。远程压缩内部算法往往不可见。

04

源码存在 ≠ 默认开启

编译特性、远端配置、provider 能力与版本共同决定生效分支。

05

历史可查 ≠ 当前已知

恢复指针要真的检索才有正文；摘要与路径不赋予权限。

06

摘要成功 ≠ 保真

前置裁剪、摘要遗漏和 fallback 都可能丢事实；需要任务级召回评估。
