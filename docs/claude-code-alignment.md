# Claude Code interaction and runtime alignment

This implementation tracks the previously agreed comparison goals. Matching a behavior here is not a claim of complete Claude Code parity. No leaked source or copied proprietary implementation is included.

| Area | Current implementation | Remaining work |
| --- | --- | --- |
| Sending and stopping | Submission identity/digest, accepted-state recovery, attachment receipt reuse, model selection serialized and pinned to the run | Live model evaluation of in-run requirement handling |
| File safety | Visible read receipts, SHA-256 checks, observed-range editing, native conditional writes; bounded actual before/after review, export and guarded conditional restore with durable receipts | New-file removal and undoing shell/network effects are unsupported |
| Commands | Actual Bash/sh, explicit exit/timeout/cancel state, retained partial output; native and Docker integration validated | Live custom images require their own runtime validation |
| Background work and output | Private ownership handles, scoped task/log APIs, bounded raw logs, independent stop and UI, restart inspection without replay; atomic helper replacement preserves running supervisors | Live ACS deployments require their own provider validation |
| Providers | Multiple tool fragments, cumulative usage normalization, safe typed failures, real text-only readiness check | Live deployments require their own provider validation |
| Context | Complete-request budget estimates, actual/missing usage ledger, persistent scoped checkpoints, tool-free validated compaction with finite recovery/circuit breaker, literal protected input and tool groups, versioned Skill body deduplication, cached task-state restoration, visible FileState rebuilt each turn | Live model evaluations for summary quality and provider-specific context estimates |
| Collaboration | Drafts and recovery instructions preserved; durable questions/Plan approval; explicit text adjustments at complete tool boundaries; snapshot-pinned next-task queue with failure/stop holds and scoped receipts | Live model evaluation of planning, clarification and changed requirements |
| Project rules | Explicit project settings rules with monotonic versions/SHA-256; immutable source/content snapshots at initial and queued acceptance; source receipt in chat | Live model evaluation of project-guidance adherence |
| Documentation and quality | Six-language UI/help maintained; PostgreSQL, native/Docker and desktop/mobile browser regressions | Live deployment/model validation remains separate from local fixture evidence |

MCP/hooks remain conditional extension work when a concrete integration needs them. This direction does not add automatic cross-conversation Memory/RAG, orchestration UI or a browser-management product.

Validation distinguishes local fixtures, real Docker commands and live cloud/provider integration. ACS fixture tests do not establish live ACS availability. Conditional file writes coordinate native helper writers; arbitrary Bash writes are outside that lock. Unknown launch receipts do not authorize a second command or a signal to an unverified process.

The file-review/project-rule batch adds migrations 023–024. Review records originate from trusted Agent write/edit handlers: a durable intent precedes mutation, private original reads confer no FileState authority, and actual native returned digests confirm the after snapshot. Each text side is bounded at 512 KiB with a 64 MiB conversation quota; unretained/unknown records never claim a diff. Existing text-file modifications can be restored explicitly under the conversation guard with an AFTER digest check; later edits, active runs, new-file removal, missing snapshots and unconfirmed restoration refuse unsafe replay. Up to 20 recent platform mutation/restore facts are included in complete-request budgets after compaction without file bodies, current-content claims or write grants. Project rules bind source/content/version/SHA-256 at acceptance, so subsequent edits or project moves do not change accepted or queued tasks.

Validation includes full backend tests with real PostgreSQL and native conditional filesystem writes; scope, actual executor/alias capture, protected partial-read authority, denied intent writes, later-edit refusal, stable restore identities, lost native receipts, active-run/new-file denial and immutable rule snapshots.
